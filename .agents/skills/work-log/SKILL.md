# work-log

현재 세션의 작업 내용을 **자기완결적인 한 장짜리 마크다운 문서**로 정리해 `docs/work-log/YYYY/MM/` 에 저장한다.

## 적용 범위

- 이 스킬은 단일 세션 작업일지 작성에 사용한다.
- 여러 작업/스프린트 추적은 `manage-cycle` 스킬을 사용한다.
- 하루치 종합 요약은 `work-log-daily` 스킬을 사용한다.

## 핵심 원칙

1. **자기완결성 (Self-Contained)**: 작업일지는 그 문서 하나만 읽어도 무슨 일이 있었는지 이해할 수 있어야 한다.
   - 다른 plan/spec/context 문서를 **링크하거나 참조하지 않는다**.
   - "자세한 내용은 X 참고" 같은 표현 금지.
   - 필요한 배경/맥락은 본문에 직접 요약해 넣는다.
2. **세션 컨텍스트 활용**: 기존 plan / `docs/cycle/` / `docs/designs/` / 대화 중 작성된 plan 등이 있다면 **참고는 하되**, 그 내용을 본문에 직접 옮겨 적는다. 외부 문서를 가리키지 않는다.
3. **사실 위주 서술**: 추측/희망사항이 아니라 **실제로 일어난 일**을 적는다. 검증되지 않은 부분은 본문에 "미검증"으로 명시한다.
4. **간결성**: 한 페이지 분량(보통 200–600단어)을 목표로 한다.

## 파일 경로 규칙

```
docs/work-log/
└── YYYY/
    └── MM/                    # 0-padding (01, 02, ..., 12)
        └── YYYY-MM-DD - 작업이름.md
```

- 프로젝트 루트 기준 상대 경로 `docs/work-log/`. 연도 4자리, 월 0-padding 2자리.
- 파일명: `YYYY-MM-DD - 작업이름.md`. 날짜는 세션 시작 시점의 현재 날짜(`currentDate` 또는 `date +%F`).
- 작업이름은 짧고 명료하게(2–6단어). 파일시스템 금지 문자(`/`, `\`, `:`, `*`, `?`, `"`, `<`, `>`, `|`) 사용 금지.

### 중복 처리

같은 디렉토리에 동일 파일명이 이미 존재하면 **덮어쓰지 않는다.** 날짜 뒤에 인덱스를 붙여 새 파일을 만든다 (`YYYY-MM-DD-2 - 작업이름.md`, `-3` …). 인덱스는 `2` 부터.

- **같은 세션을 재기록하는 경우는 인덱스 신규 생성이 아니라 기존 파일에 "## 이후 추가 작업" 섹션을 append 한다.** 인덱스 신규 생성은 명확히 다른 세션이거나 사용자가 분리를 명시한 경우에만.

## 문서 포맷

작업일지는 정확히 다음 4개 섹션을 가진다. **순서 고정, 제목 고정.**

```markdown
# 작업 이름

## 요약

3–5문장으로 무엇을 / 왜 / 결과를 압축. 처음 보는 사람도 이 섹션만 읽으면
무슨 작업이었는지 파악할 수 있어야 한다. 외부 문서 참조 금지.

## 내용

실제로 한 일을 시간 순 또는 논리 순으로 정리. 다음을 포함:
- 변경된 파일/모듈/문서 (프로젝트 루트 기준 상대 경로, `path:line` 권장)
- 주요 결정과 그 이유
- 사용한 도구/명령 (있다면)
- 검증한 내용 (테스트, 빌드, 수동 확인 등)
- 남은 작업 / TODO (있다면)

## 기존 계획과의 차이

세션 진입 시 가지고 있던 plan / 의도 / 기대치와 실제 결과의 차이를 적는다:
- 계획대로 진행된 부분 / 계획과 달라진 부분과 그 이유
- 의도적으로 빼거나 추가한 범위 / 막혀서 보류한 부분

계획이 명시적으로 없었다면 "계획이 명시적으로 없었음. 다음 항목을 즉흥적으로 결정함:" 형식으로 적는다.
```

- **"기존 계획"의 의미**: 사용자가 세션 시작 시 제시한 요구사항, 또는 세션 중 합의된 접근(plan, brainstorming 결과, 명시적으로 동의한 방향)을 기준으로 한다. 머릿속 막연한 가정은 "기존 계획"이 아니다.
- **민감 정보 금지**: API 키, 토큰, 비밀번호, 개인정보를 본문에 적지 않는다.

## 절차 (체크리스트)

1. **세션 컨텍스트 수집**
   - 이번 세션에서 실제로 변경한 파일/문서/명령을 떠올린다.
   - `docs/work-log/raw/<오늘 날짜>.jsonl` 이 존재하면 읽어서 변경 파일 목록·타임라인·턴별 프롬프트를 보강한다. 이 파일은 합성 소스일 뿐이며, 본문에 경로를 링크하거나 "raw 로그 참고" 식으로 언급하지 않는다.
   - 세션 시작 시 사용자가 제시한 요구사항, 진행 중 만든 plan / TodoWrite 를 참고한다.

2. **작업이름 결정** — 짧고 검색 가능한 이름. 모호하면 사용자에게 1줄로 확인한다.

3. **저장 경로 계산** — `docs/work-log/YYYY/MM/YYYY-MM-DD - 작업이름.md`. 디렉토리가 없으면 `mkdir -p`.

4. **중복 검사** — 동일 경로 파일이 있으면 인덱스(`-2`, `-3` …)로 미사용 파일명을 찾는다. 기존 파일을 덮어쓰지 않는다.

5. **문서 작성** — 위 4개 섹션 포맷 그대로. 외부 문서 링크/참조 금지. 사실과 추측을 분리("미검증" 표시).

6. **이월 항목 에스컬레이션 확인** — 본문의 "남은 작업 / TODO"에 **블로커/추적 필요 항목**이 있으면 `docs/cycle/backlog.md`(또는 사용하는 이슈 트래커)에 등록 여부를 확인하고 미등록이면 등록을 제안한다.

7. **저장 후 보고** — 저장 경로를 1줄로 보고 (예: `docs/work-log/2026/05/2026-05-27 - work-log 스킬 추가.md`).

## 자주 하는 실수

| 실수 | 교정 |
|------|------|
| "자세한 내용은 `docs/designs/X.md` 참고" 식 외부 링크 | 해당 내용을 본문에 직접 요약해 넣는다. |
| 같은 파일명이라 그냥 덮어씀 | 인덱스(`-2`, `-3`)를 붙여 새 파일 생성. |
| 월을 `2026/5/` 로 저장 | 0-padding(`2026/05/`) 사용. |
| "기존 계획과의 차이"를 비워둠 | 차이가 없으면 "계획대로 진행됨". 계획이 없었으면 그렇다고 적는다. |
| 추측을 사실처럼 기술 | 검증한 범위까지만 단정. 나머지는 "미검증". |
| raw JSONL 경로를 본문에 링크 | raw 는 소스다. 내용을 본문에 옮겨 적고 경로는 언급하지 않는다. |

## Red Flags

- 본문에 `참고:`, `자세한 내용은`, `[…](…)` 같은 외부 문서 참조가 있다.
- 같은 파일명을 그대로 덮어쓰려고 한다.
- "기존 계획과의 차이" 섹션이 비어있거나 "없음"으로만 채워져 있다.
- 작업이름이 막연하다 (`작업`, `수정`, `업데이트`).
- 검증하지 않은 내용을 단정형으로 적고 있다.
