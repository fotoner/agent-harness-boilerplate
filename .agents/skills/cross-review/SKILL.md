# cross-review

두 모델의 독립 리뷰를 실행하고, 결과를 수렴 분류한 뒤, **반영 여부까지 확인**하고 마무리한다.

## 핵심 원칙

1. **모델 교차성**: 교차 리뷰의 가치는 서로 다른 모델의 독립 시각이다. **같은 모델로 절차만 두 번 도는 것은 교차 리뷰로 치지 않는다.**
2. **범위 먼저**: 리뷰 대상과 범위(브랜치 diff 베이스, 문서 경로, 데이터 기간)를 확인하고 시작한다.
3. **보고로 끝내지 않는다**: 수렴 결과를 나열만 하고 멈추지 않는다. 반영 여부를 묻거나, 지시가 이미 있으면 반영까지 수행한다.

## 절차 (체크리스트)

1. **리뷰 범위 확인**
   - 대상: 브랜치 diff(베이스 커밋 명시) / 문서(경로) / 데이터 분석(기간·소스).
   - 사용자 지시가 모호하면 범위를 1줄로 확인받고 시작한다.

2. **1차 + 2차 리뷰 실행 (모델 교차성 보존)**
   - **1차**: 현재 세션 모델로 리뷰를 수행한다 (코드 diff 리뷰 / 문서 리뷰 / 분석 검증).
   - **2차**: 독립적인 두 번째 모델로 리뷰한다. 예: 별도 CLI(Codex 등) 호출, `claude -p` headless 호출, 또는 다른 세션. 보일러플레이트가 gstack 기반이면 gstack 의 리뷰/`codex` 래퍼 절차를 사용한다.
   - 두 번째 모델 호출이 불가한 환경이면: 단일 모델 리뷰임을 보고에 **명시**하고, 모델 교차가 필요하면 반대 하네스 세션에서의 실행을 권고한다.
   - 두 리뷰는 서로의 결과를 보지 않은 **독립** 실행이 원칙. 1차 결과를 2차 리뷰어 prompt 에 노출하지 않는다.

3. **수렴 분류**
   - **공통 지적 = P1** (두 모델이 독립적으로 동의 — 신뢰도 높음)
   - **단독 지적 = P2** (한쪽만 — 검토 가치 있으나 오탐 가능)
   - **상충 = 별도 표기** — 양쪽 근거를 나란히 제시하고 판단 근거와 함께 의견을 밝힌다.

4. **반영 게이트**
   - "P1부터 반영할까요?" 를 묻는다 (또는 사전 지시가 있으면 바로 반영).
   - 승인 시 수정 실행 → 반영 내역 보고. 보류 시 보류 항목과 사유를 명시 기록.

5. **보고**
   - 분류 결과(P1 n건 / P2 n건 / 상충 n건) + 반영/보류 내역 + 어느 모델이 무엇을 지적했는지를 요약한다.

## 자주 하는 실수

| 실수 | 교정 |
|------|------|
| 같은 모델로 리뷰 절차 2개 실행 후 "교차" 표기 | 단일 모델 리뷰임을 명시. 2차는 독립 모델. |
| 두 번째 모델 세션에서 같은 모델 재호출 | 자기 자신과의 교차는 무의미. |
| 리뷰 결과 나열 후 종료 | 반영 게이트까지가 이 스킬이다. |
| 범위 미확인 시작 | 베이스/기간/경로를 먼저. |
| 1차 결과를 2차 리뷰어 prompt 에 노출 | 독립 실행 원칙 위반 — 수렴 단계에서만 합친다. |

## Red Flags

- 두 리뷰 결과의 출처(어느 모델)를 구분하지 않고 섞어 보고하고 있다.
- 상충 항목을 한쪽 의견만으로 정리했다.
- P1 항목이 있는데 반영 여부를 묻지 않고 턴을 끝내려 한다.
