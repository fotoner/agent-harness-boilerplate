# 이슈 관리 규칙

사람과 에이전트 모두 할 일·조사·계획을 GitHub 이슈로 관리한다. 계획 문서를 따로 만들지 않는다.

## 범위

{{이 프로젝트가 받는 이슈와 받지 않는 이슈. 받지 않는 이슈는 이유를 적고 "not planned"로 닫는다}}

## 제목

마침표 없는 한 줄로 쓴다. 종류는 라벨로 나타내므로 `[기능]` 같은 머리말을 붙이지 않는다.

| 종류 | 제목에 쓸 것 | 예 |
|---|---|---|
| 기능·정리·조사 | 할 일 | `검색 결과를 태그로 거르기` |
| 버그 | 무엇이 어떻게 잘못되는지 | `저장한 뒤 목록이 갱신되지 않음` |
| 상위 이슈 | 주제 이름 | `내보내기·가져오기` |

## 라벨

이슈마다 **종류 1개 + 영역 1개 이상 + 우선순위 1개**를 붙인다. 막힌 이유가 있으면 `needs:` 라벨을 더한다. 라벨은 `scripts/labels.sh <영역…>`로 만든다.

| 묶음 | 라벨 | 뜻 |
|---|---|---|
| 종류 | `feature` | 새 기능·기능 개선 |
| | `bug` | 잘못 동작함 |
| | `research` | 결과가 지식인 일. 결론은 댓글과 문서로 남긴다 |
| | `chore` | 정리·리팩터링·빌드·도구 |
| | `perf` | 동작을 유지하는 성능 측정·개선 |
| | `docs` | 문서 |
| | `epic` | 상위 이슈. 하위 이슈를 묶기만 하고 직접 작업하지 않는다 |
| 영역 | `area:{{영역}}` | {{영역의 뜻}} |
| 우선순위 | `P0` | 데이터 손실·보안·운영 장애. 하던 일을 멈추고 먼저 |
| | `P1` | 다음에 할 것 |
| | `P2` | 할 것, 순서 미정 |
| | `P3` | 아이디어. 할지 아직 정하지 않음 |
| 막힘 | `needs:decision` | 사람이 정할 것이 남음(무엇을 정해야 하는지 본문이나 댓글에 적는다) |
| | `needs:device` | 실기기·실물 확인이 있어야 진행됨 |
| | `needs:experiment` | 사용자가 직접 해 보는 실험이 있어야 진행됨 |

- 다른 이슈가 먼저 끝나야 하면 라벨 대신 "blocked by" 관계를 건다(`gh issue edit N --add-blocked-by M`).
- 영역 라벨은 같은 영역 이슈가 3개 이상 모이면 만든다. 새 라벨은 이 표에 먼저 더한다.
- 중복이나 안 하기로 한 이슈는 라벨 대신 닫는 이유(`duplicate`, `not planned`)로 나타낸다.

## 본문

템플릿(`.github/ISSUE_TEMPLATE/`)의 섹션 가운데 필요한 것만 남겨 쓴다.

| 종류 | 섹션 |
|---|---|
| 기능·정리·문서 | `## 배경` · `## 목표`(닫는 기준) · `## 할 일` · `## 참고` |
| 버그 | `## 증상` · `## 재현` · `## 기대` · `## 환경` |
| 조사 | `## 질문` · `## 방법` · `## 결론` |
| 상위 | `## 목표` · `## 순서` · `## 범위 밖` |

- `## 할 일`에는 한 브랜치로 끝낼 크기의 일을 한 줄씩 적는다. 따로 브랜치·실험·결정이 필요한 일은 하위 이슈로 뺀다.
- 상위 이슈의 하위 이슈 목록은 GitHub 하위 이슈 기능이 보여 주므로 본문에 옮겨 적지 않는다.
- 규칙을 확정하면 `docs/<주제>.md`로 옮기고 이슈에는 링크만 남긴다.

### 조사 댓글

- 조사 결과는 `## 조사 N — 주제 (YYYY-MM-DD)` 제목의 댓글로 쌓고, 결론을 먼저 쓴다.
- 주장마다 근거 수준과 근거 링크를 붙인다.

| 근거 수준 | 뜻 |
|---|---|
| **[확인]** | 공식 자료, 여러 출처 일치, 직접 검증 |
| **[제3자]** | 한 프로젝트나 한 사람의 경험 |
| **[추정]** | 추론 |

### 공개 저장소에서 넣지 않는 것

- 실데이터 사본과 그 내용, 개인 경로
- 토큰·키·자격 증명, 로그 원문(인증값이 섞일 수 있다)
- 사용자 이름, 기기 일련번호, 대화에서 들은 내용의 출처가 된 사람. 내용만 옮기고 근거 수준을 [제3자]로 적는다.

## 흐름

1. **만들기**: 템플릿 섹션을 채우고 종류·영역·우선순위 라벨을 붙인다. 큰 주제의 일부면 상위 이슈 아래에 둔다(`--parent N`).
2. **고르기**: `P0` → `P1` → `P2` 순으로 고른다. 막히지 않았고 `needs:` 라벨이 없는 이슈는 에이전트 혼자 진행할 수 있다.
3. **작업**: `{{DEFAULT_BRANCH}}`에서 `<type>/<번호>-<짧은-이름>` 브랜치를 딴다. 화면이 바뀌면 같은 조건으로 바꾸기 전·후 화면을 캡처한다. 화면이 바뀌지 않으면 실행 명령과 결과를 텍스트로 남긴다.
4. **막힘**: 맞는 `needs:` 라벨을 붙이고 무엇이 필요한지 댓글로 적는다. 실험이면 무엇을 어떻게 해 달라는지까지 적는다.
5. **닫기**: `{{DEFAULT_BRANCH}}`에 합칠 때 닫는다. 닫는 댓글에는 합친 커밋과 확인한 것(실행한 명령과 결과)을 적는다. 안 하기로 했으면 이유를 적고 "not planned"로 닫는다.
6. **마일스톤**: 릴리스 버전을 정하면 마일스톤을 만들고 넣을 이슈를 묶는다.

### 자주 쓰는 명령

```bash
gh issue list -l P1                                   # 다음에 할 것
gh issue list -l needs:decision                       # 사람이 정할 것
gh issue list --search 'is:open -is:blocked -label:epic -label:needs:decision -label:needs:device -label:needs:experiment'
                                                      # 에이전트 혼자 진행할 수 있는 것
gh issue create -T 기능 --parent 3 -l feature,area:{{영역}},P2   # 템플릿으로 하위 이슈 만들기
gh issue edit 39 --add-blocked-by 38                  # #38이 끝나야 #39를 할 수 있음
gh issue close 16 -c "합침: <커밋>. 확인: <실행한 명령과 결과>"
```
